Why the layers are materialised the way they are. Staging is views — a rename and a cast over one seed; copying the data would buy nothing and create a second copy to drift. Cleansed is tables — identity resolution is the expensive, opinionated part, and computing it once means every mart reads the same answer rather than each recomputing the match ladder. Unified is views only — always current, nothing to schedule, no “when was this last refreshed?”.

03 · Before any SQL

Read the data first

163 rows across 77 columns, profiled before a single model was written. Eight questions decided the whole architecture — the answers are why the identity spine, the surface rules and the match ladder look the way they do.

QuestionWhat the data saidSo
Is one user_id one person? No 9 logins, 8 people. grace@acme.com signed up twice. Exact-email merge; both ids kept.
Does a person belong to one org? No Two logins sit in two orgs, and Frank's two orgs belong to two different accounts. Person→account only when all orgs agree.
Does every org have a CRM account? No Five of six map, and one of those only through a fallback rule. Unmapped orgs are prospects, not errors.
Do objects belong to their creator's org? Yes All 31 of them. project → org is the safe attribution path.
Does anything name the client or surface? No No column records a client, surface, user-agent or which API key created an object. Surface must be inferred from side-effects — and labelled as such.
How much origin evidence is there? 17 of 22 experiments carry repo_info; across all 31 objects, 12 have none at all. 12 objects are unknown, never guessed as UI.
Do the external identifiers join as delivered? No Not one vendor website equals a CRM domain literally. Ten non-null websites arrive in seven shapes. Normalise first, then match. That's when hooli.com turns out to belong to two accounts.
What window does the data cover? Everything ends 2026-07-27; traces rise exactly 0.7 GB/day for every org, so clearly synthetic. Every window runs from a frozen as_of_date, never current_date.

What a user_id on an object actually is. The login whose session or API key made the call — not necessarily a human. Bob's twelve experiments run nightly between 02:01 and 02:12 with ci_run_id = gha-10xx, author_name = ci-runner, under a key named ci-service. That's a GitHub Action. So the actor is classified separately from the login: Bob is an automation_identity, his runs prove the account uses the SDK, and he is never counted as a member using the product. In dim_members that reads sdk_evidence = no_evidence beside sdk_evidence_any_actor = usage_proven — the machine is visible without being mistaken for a person.
05 · Part A

Surfaces: what each signal can and cannot prove

Nine signals, each with a surface, an evidence kind, an attribution class and a confidence — all of it a row in ref_surface_signals, not a CASE statement. Click one to see what it is honestly worth.

What can be proven

UI is deterministic — a logged-in page view is a page view. SDK is deterministic for 18 of 31 objects and heuristic for one more, on repo_info and CI tags, plus org-level proof from trace ingestion.

What cannot

CLI usage is not observable — the wizard is a browser event and a key name is free text. MCP the same. Both are capped at intent_only, and a test called cli_and_mcp_never_claimed_as_usage fails the build if anyone ever changes that.

Where the proof sits matters as much as whether it exists. Initech reads sdk: usage_proven while pct_members_usage_proven = 0 — because the only evidence is the org's trace ingestion, and no individual member can be shown to have written code. evidence_level says org rather than member for exactly that row, so no dashboard can render the status without the caveat.
06 · Part B — the CDP core

External → account resolution

Not one vendor website equals a CRM domain as delivered. Normalisation happens once, in plain SQL — lower, trim, strip, split — and then four rules decide. Pick a company to see the keys it produced, what each one pointed at, and why it landed where it did.

The four rules

  1. Only a key pointing at exactly one account may decide.
  2. The highest-precedence deciding key wins: LinkedIn slug › website domain › LinkedIn-reported domain.
  3. Every other key that matched must agree, or it's a conflict and nothing is assigned.
  4. Names never decide. A name pointing elsewhere costs 0.20 and holds the match for a steward.

Normalisation, worked

https://www.Acme.com/products?utm=x → acme.com
http://globex.io/products → globex.io
https://piedpiper.com/?utm_source=news → piedpiper.com
…/company/pied-piper/ → pied-piper
http://uk.linkedin.com/company/Acme-Corp/?trk=abc → acme-corp

The last line is a country sub-domain — a shape the brief names but the seeds don't contain. It's covered by a dbt unit test, not by hope.

Unresolved leaves through two doors, not one. The brief asks that unresolved companies be kept — none are dropped. But “kept” isn't “prospected”. sc10 Prospect AI has clean keys and simply has no account, so it's a net-new prospect. sc11 is a duplicate Acme record and sc07 has no identifiers at all: for both, an account almost certainly already exists, and putting them on a prospecting list would be a second error stacked on the first. They go to the review queue with the reason attached, and assert_every_external_company_has_one_output proves each of the eleven takes exactly one door.

10 · The memo

Six questions, answered

The full text is in MEMO.md. These are the answers in short.

Q1 Is surface attribution deterministic, heuristic, or impossible?
SurfaceAttributionColumns it rests on
UIDeterministicraw_segment_pages.user_id, path
SDKDeterministic for 18 of 31 objects, heuristic for 1 more — and impossible to separate from the CLIrepo_info; metadata.ci_run_id / ci / source; raw_trace_volume (org × day)
CLIImpossible for usage; heuristic for intentraw_cli_wizard (a browser event); raw_api_keys.name containing “cli”
MCPImpossible for usage; heuristic for intentraw_docs_mcp_events.action

Nothing in the eighteen files names a client, user-agent or key id, so the CLI — which wraps the SDK — cannot be separated from it, and the twelve objects carrying neither field are recorded unknown, not SDK.

Q2 How would you measure whether the matching is good — and precision or recall?

Five things, all recomputed by rpt_resolution_quality on every run: precision on a monthly steward-labelled sample split by match_method, with a 98 % bar for anything a rep sees; coverage (8 of 11 companies carry an account, though only 7 deliver signals); corroboration (4 of 8 matches rest on two or more independent keys); conflict and ambiguity rates as drift alarms; and how often reps click “wrong account”.

Precision, every time. A bad merge sends a rep another company's news and costs the tool its credibility; a miss just sits in a queue where someone can still find it. That single stance is what produced all four precedence rules.

Q3 “What % of the account is using the CLI?”

Not truthfully, no. For Globex I'd give three numbers: CLI usage is not measurable; setup intent covers 1 of 3 known product members, with a second not counted because he belongs to two accounts; and code-based usage by a person — which cannot be split between SDK and CLI — is 1 of 3, plus a CI job under a member's key.

I won't give a CLI percentage, won't infer CLI from repo_info or key names, and would drop “% of the account” altogether: the denominator is product members, not headcount. cli_and_mcp_never_claimed_as_usage keeps that honest in code, and account_360.adoption_in_plain_english carries those exact sentences to the rep.

Q4 One instrumentation change, one data addition

Product. Captured at the API gateway from the client user-agent or MCP server id: stamp client_surface, client version and api_key_id on every write. Stored denormalised on the object tables and in a new api_request_log. CLI and MCP become deterministic, SDK separates from CLI, and service keys identify themselves.

CRM. Captured from an enrichment vendor at account creation and on refresh. Stored as required website_domain and linkedin_company_url on Account, plus a populated ParentId. Missing identifiers cause most non-matches; the hierarchy lets Hooli and Hooli XYZ roll up without merging.

Q5 What sales motion does this serve, and how would you know it's useful?

Expansion. Usage surges on non-Enterprise plans, CLI and MCP intent as an enablement opening, and funding / launch / hiring news. net_new_prospects feeds a product-led motion into sales alongside it.

Two leading indicators say whether it's working — do reps open the 360, and what share of signals get acted on rather than dismissed. Two lagging ones settle it: signal-sourced pipeline and expansion ARR, measured against a random holdout. A signal type with no lift, or more than ~70 % dismissed, gets cut.

Q6 How would you find which signals actually drive value?
  1. Fix the outcome first: an opportunity, upgrade or expansion within 30–90 days.
  2. Snapshot fct_account_signals daily. It's already one shape, so it doubles as the feature store and joins straight to opportunities.
  3. Per signal type, measure lift over baseline (controlled for plan and size), lead time and precision at top-N. Then learn weights to replace the v0 rules — keeping the reasons visible.
  4. Use holdouts so signals don't take credit for deals that would have closed anyway, treat rep dispositions as labels, and retire whatever shows no lift.
Where I'd invest next, in order. ① Surface telemetry — client_surface and api_key_id on every write turns CLI and MCP from unmeasurable into deterministic. ② A labelled match set of 100–200 steward-verified pairs, so precision is measured rather than assumed. ③ History — snapshot the 360 and the signal feed daily; you can't learn which signals drive pipeline without knowing what a rep saw and when. ④ Account hierarchy, so Hooli and Hooli XYZ roll up without anything being merged. ⑤ Delivery — reverse-ETL into Salesforce tasks or Slack with a “wrong account” button feeding straight back into the scorecard.
